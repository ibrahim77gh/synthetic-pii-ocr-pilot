Synthetic PII OCR Pilot

A small working pipeline for a synthetic document OCR dataset: forms, invoices and ID-style cards, with a bounding box on every personal-data field. All 300 documents were generated and checked by the two scripts in the source repository. Every number here comes from that run.

      How the documents are generated
      
    
      
    
      
      
      
        
      Values
      
        
      Each page gets one fresh synthetic person from Faker in one of six locales (en_US, en_GB, de_DE, fr_FR, it_IT, nl_NL). Local formats are kept: dates follow the locale with some ISO dates mixed in, postcode and city swap order on EU addresses, and US pages carry SSNs and cards where EU pages carry IBANs. Emails are built from the person's own name, as they usually are in real documents.
      
      
      
      
      
        
      Layouts
      
        
      Three templates: form, invoice and ID-style card. Each varies font (7 families), field order, key wording ("Surname" or "Family name"), boxed or underlined inputs, and colour. Every page also contains text that is not personal data and stays unlabelled on purpose: company names and addresses, invoice and due dates, expiry dates, form references and amounts.
      
      
      
      
      
        
      Scan effects
      
        
      {{ROTATED}} of the {{DOCS}} pages are rotated by up to 1.5°. Pages also get mild blur, contrast and brightness shifts, grain and JPEG compression. Boxes are transformed with the page. Each field stores its rotated four-corner quad and the axis-aligned bbox around it.
      
      
      
      
      
        
      Key–value links
      
        
      Each field also stores the printed label it belongs to (key_text, key_bbox), so the same data can train key–value extraction as well as PII detection.
      
      
      
    
      
  
      

  
      
    
      
      
      Output format
      
      
      One JPEG per page, one JSONL record per page, and a flat Parquet file with one row per field for quick analysis in pandas or polars.

      Quality checks
      
      
      The first check runs during generation. The other eight are in validate.py, which reads only what is on disk, writes qc_report.json and exits non-zero on any failure, so it can block a release.
      
    
      
    
      
      
      
        
      CheckHowResult
      
        
          
      Text sits inside its boxEvery value is also drawn onto a hidden mask, with its own pixel value, and the mask is rotated with the page. Each field's real ink extent from the mask must sit inside its stored box, within 2 px. This catches geometry bugs that a box-in-bounds check would miss.{{RENDER}}
      
          
      Boxes validInside the image, at least 3 px wide and tall, and the image size matches the record.0 failures
      
          
      No overlapping fieldsPage rotation is read back from the quads and undone first, so tilted neighbouring lines aren't flagged by mistake.0 failures
      
          
      Values match their labelIBAN mod-97 checksum, card Luhn check, each date parses back to its stored ISO value, SSN and ID patterns, phone digit count, no digits in names.0 failures
      
          
      Text still visibleAfter blur, grain and JPEG, the darkest pixels inside each box must cover at least 2% of it. Lowest seen: {{MIN_INK}}.0 failures
      
          
      No duplicate pagesSHA-256 of every image file.0 failures
      
          
      No duplicate peopleOne person_id (hash of name and date of birth) per page.0 failures
      
          
      Unique values stay uniqueEmail, phone, ID number, SSN, IBAN and card number never repeat. Names and cities may repeat, as they do in real data.0 failures

      Reproducibility. Two runs with the same seed produce byte-identical files ({{NFILES}} of {{NFILES}}). Two fixes were needed to get there. Pillow's effect_noise uses its own random generator, which the seed doesn't control, so the grain is now drawn from the seeded one. Faker builds its Italian city list from a Python set, so the order changed with each process's hash seed and the same seed gave different cities. The generator now sorts that list.
      
  
      

  
      
    
      
      
      Labels and a mapping to Presidio
      
      
      Field counts from this run, with each label's nearest Microsoft Presidio entity. Several labels merge into one Presidio entity (both name labels become PERSON, three address labels become LOCATION), so mapping back is lossy and the mapping keeps track of that. Labels with no Presidio equivalent are listed as unmapped, never quietly dropped.

      Speech pilot: putting PII spans on the audio timeline
      
      
      This part is a design, not yet built: how labelled text spans get aligned to timestamps in generated audio.
      
    
      
    
        
      
      1. Turn the text into what will be spoken, keeping an offset map
        Written PII isn't spoken as written. j.doe@mail.com becomes "j dot doe at mail dot com", and an IBAN is read in digit groups. I would convert each span to its spoken form and keep a character map from written to spoken offsets, so every label still points at the right words after conversion.
        2. 
      
      2. Generate the audio
        Open-weight TTS on the GPU machine, with several voices and speaking rates per sentence. Each model and voice gets a licence check first. For example, Kokoro-82M is Apache-2.0, but XTTS-v2 is under the Coqui Public Model License, which is non-commercial, so it can't feed the commercial datasets.
        3. 
      
      3. Force-align words to the audio
        Montreal Forced Aligner, or a CTC aligner such as the one in WhisperX, gives start and end times for every spoken word. If the TTS engine reports its own word timings, I would use them and keep the aligner as a cross-check.
        4. 
      
      4. Project each span onto time
        Spoken span, then the words it covers, then [first word start, last word end] with about 30 ms of padding. Each record keeps the written offsets, the spoken offsets and the seconds.
        5. 
      
      5. Check every clip
        Re-transcribe each clip with Whisper and flag clips where the character error rate inside a PII span is over a set limit. Mispronounced IBANs and emails are the usual failure. Also check that timestamps increase and stay inside the clip, flag clips that are unusually slow or fast per character, and listen to a random sample from each voice.
        6. 
    
      
  
      

  
      
    
      
      
      Merging existing text datasets
      
    
      
    
        
      
      • Deduplicate on masked text, not raw text. Two rows that differ only in the name dropped into them are the same sentence. Replacing each span with its label ([GIVENNAME] paid [IBAN]) before hashing catches those duplicates.
        • 
      
      • Exact hashing first, then MinHash-LSH on word shingles for near-duplicates. Set the similarity threshold on a hand-checked sample before applying it.
        • 
      
      • Check that every span is still correct after each normalisation step: text[start:end] == value, so no offset quietly shifts.
        • 
      
      • Carry source dataset, version, licence and original row id through every merge, so any row can be traced and removed if a source licence changes.
        • 
    
      
  
      

  
      
    
      
      
      Licences and provenance in this pilot
      
    
      
    
        
      
      • Values come from Faker (MIT). Some of Faker's locale data comes from other sources. Its Italian place names, for example, are converted from GeoNames postal data (CC BY 4.0), which needs attribution in a public release.
        • 
      
      • The pilot renders with Windows system fonts. That is fine while the pilot is private. For a public release I would render with OFL-licensed fonts (Noto, Liberation) so every input has a clear licence.
        • 
      
      • Every record stores the generator version, seed, and Faker and Pillow versions.
